# #1340 replay guard: never return a replayed result as fresh (2026-10-13)

## Review finding addressed

The maintainer disposition of `ab836ac7` used this negative control. A status poll `read({path})` returned
`running`. After a backend replacement, the next identical read was legitimate, but the guard answered it with the
recorded `running` instead of dispatching it. Name and arguments do not identify an operation.

## Change

In a replayed run, before any call has been sent to the client, the first request identical to a completed tail
call is not executed. It gets a not-executed notice (`is_error`) that names the delivered `tool_use_id` whose result
is already in the history, and it carries no client content. Repeating the call after the notice dispatches it to
the client. `completedToolTail` keeps only delivered ids, not results.

This is not exactly-once. A model can repeat through another tool, or repeat on purpose after the notice.

## Deterministic negative control

`src/__tests__/antigravity-replay-duplicate.test.ts`, test "a polled status is read fresh, never answered stale".
The history holds a `read` that returned `running`; the fixture model reads the same path twice after the replay.

| Source | Result |
| --- | --- |
| `ab836ac7` guard (with current main) | `REPLAYED:running\|done`: the stale value was returned as the first read |
| this revision | `REPLAYED:<notice>\|done`: the second read reached the client as `tool_use` |

## Live: actual Pi on macOS

Harness: `scripts/e2e-antigravity-replay-poll.mjs`. Pi polls a status file that says `running`. After Pi's first
read completes, the relay changes the file to `done` and replaces the backend before forwarding that result. The
next request is a completed-history replay.

Environment:

- MacBook Air, Darwin arm64 (macOS 14.8.9); Node v22.23.2; Pi 1.1.0 (`@earendil-works/pi-coding-agent`).
- `gemini-3.8-flash-low`; `useG1Credits false`.
- official agy **1.3.3**, sha256 `96dd362d…370d`, the same before and after the runs.

Qualification: the official installer only serves the latest CLI. For these runs, both builds had one local,
uncommitted change that also accepts `1.3.3` in the exact `1.2.7` version gate. No other source was changed.

What the model received on its first re-read after the replay, taken from agy's own conversation transcripts:

| Build | Run | Re-read after replay received | Then | Client reads | Final |
| --- | --- | --- | --- | --- | --- |
| `ab836ac7` (+gate) | 1 | `running` (file already `done`) | read again | running, done | done |
| `ab836ac7` (+gate) | 2 | `running` (file already `done`) | read again | running, done | done |
| this revision (+gate) | 1 | not-executed notice | read again | running, done | done |
| this revision (+gate) | 2 | not-executed notice | read again | running, done | done |

The guard fired once in every run. Gemini kept polling in all four runs, so the final outcome is the same. The
difference is what the previous guard presented to the model as a fresh read: `running`, after the file had already
changed to `done`. A model that reads once and reports would have reported the stale status. The revision never
does this; the repeated read reached Pi.

The existing recovery gate also passed with this revision:
`E2E_AGY_RECOVERY=1 E2E_CLIENT=pi node scripts/e2e-antigravity-clients.mjs`. It passed all 12 checks over 7
requests, including "backend restart between client tool execution and result delivery; no repeated completed
tool", steering, compaction and abort.
